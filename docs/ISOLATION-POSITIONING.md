# dsh-cloud 隔离定位

> 2026-09-16。本文回答三个问题：**这个平台在隔离什么**、**要隔离到什么程度**、
> **为什么选了 Docker + 纵深防御这条路**。
> 通用 Docker 隔离手段见 [CONTAINER-ISOLATION](CONTAINER-ISOLATION.md)；
> 逐项实现现状见 [ARCHITECTURE](ARCHITECTURE.md) §四/§五；
> 决策记录见 [DECISIONS](DECISIONS.md)。

---

## 一、平台是什么

dsh-cloud 把 [dsh](https://github.com/deepseek-ai/deepseek-harness)（DeepSeek 开源的
AI agent harness）做成一个**自部署的多用户平台**：

- 装在一台 Linux 服务器上
- 管理员用邀请链接加人（没有公开注册）
- 每人拿到一个隔离的工作空间——一个跑着 dsh 的容器，有独立的网络、存储、资源配额
- 访问必须经过平台认证（不能被别人直接打开）
- 升级 dsh 版本不丢用户的文件、配置、插件

**核心闭环**：建实例 → 起带配额 / 卷 / 路由的隔离 dsh →
只有认证过的 owner 能访问 → 升级不丢内容。

## 二、在隔离什么

### 2.1 工作负载特征

dsh 是一个**编码 agent**。它的日常操作包括：

| 操作 | 举例 |
|---|---|
| 执行任意 shell 命令 | `npm install`、`pip install`、`cargo build` |
| spawn 大量子进程 | agent 并行跑测试、编译、lint |
| 读写文件系统 | 创建项目、修改配置、装全局 CLI 工具 |
| 发起网络请求 | 拉 npm / pip 包、访问 API、clone Git 仓库 |
| 长时间运行 | 开发服务器、文件监听、后台进程 |

**这些都是 dsh 的本职工作，不是需要阻止的异常行为。**
隔离的目标不是阻止这些操作，而是**把它们的影响范围限制在单个实例内**。

### 2.2 威胁模型

所有设计从这个前提出发：**实例 = 不可信代码执行环境。**

具体的威胁场景：

| 威胁 | 来源 | 说明 |
|---|---|---|
| **恶意或失控的 agent 行为** | agent 自身 | agent 可能执行用户未预期的命令、消耗过多资源、或被 prompt injection 操纵 |
| **跨实例窥探** | 被攻陷的实例 | 一个实例试图访问另一个实例的网络端口、文件、或凭据 |
| **宿主攻击** | 被攻陷的实例 | 实例试图访问宿主上的服务（SSH、数据库、控制面 API） |
| **资源耗尽** | 任一实例 | fork bomb、写满磁盘、内存泄漏——不应影响其他实例和宿主 |
| **信息泄漏** | 共享内核 | 实例通过 `/proc`、`sysinfo(2)` 等途径读到宿主的硬件指纹或邻居的负载模式 |
| **Web 层跨实例** | 浏览器 | 实例子域上的 agent 生成页面，利用同站 cookie 向控制面 API 发请求 |

**不在威胁模型内的**（= 选择接受、或归属不同层）：

| 不管的 | 原因 |
|---|---|
| 容器逃逸（内核级） | 共享内核的结构性限制，Docker 加固只降低概率、不消除。根治需要更强运行时 |
| dsh 内部的密钥管理 | 那是 dsh 自己的产品功能，平台不替它做决策（D9） |
| 用户自带的不可信第三方插件 | 当前不允许，是重审运行时的触发条件之一 |
| 对宿主运营者的加密 | 有宿主 / Docker 权限的人能访问底层存储，应用层限制不替代静态加密 |

### 2.3 隔离的四条通道

被攻陷的实例能跨出去的通道只有四条，每条对应一种隔离手段：

```
         ┌─────────────────────────────┐
         │  实例容器 (dsh + agent)      │
         │  ──────────────────────     │
         │  可以执行任意命令            │
         │  可以读写 /data              │
         │  可以发起网络请求            │
         └──────────┬──────────────────┘
                    │
        ┌───────────┼───────────┐
        │           │           │
   ┌────▼────┐ ┌────▼────┐ ┌───▼─────┐ ┌──────────┐
   │  网络   │ │  文件   │ │  凭据   │ │  控制面  │
   │         │ │         │ │         │ │          │
   │ 每实例  │ │ 独立目录│ │ 零跨实例│ │ 入口门  │
   │ 独立网络│ │ + 硬配额│ │ 共享凭据│ │ 经宿主  │
   │ + 回环  │ │         │ │         │ │ 回环转发│
   │ 发布    │ │         │ │         │ │         │
   └─────────┘ └─────────┘ └─────────┘ └──────────┘
```

## 三、信任等级定位

### 3.1 业界四档

按工作负载的信任等级选运行时，是业界共识的分类方式：

| 档位 | 信任等级 | 典型场景 | 运行时 |
|---|---|---|---|
| ① | **可信** | 内部微服务、CI/CD | 标准 Docker |
| ② | **半可信** | 托管开发环境、agent 工作区 | 加固后的 Docker + 纵深防御 |
| ③ | **不可信** | 公开代码沙箱、FaaS | gVisor / microVM |
| ④ | **敌意** | 恶意软件分析、CTF | 独立 VM / 裸金属 |

### 3.2 dsh-cloud 在第 ② 档

**判定依据：**

| 因素 | 本平台的情况 | 指向 |
|---|---|---|
| 谁控制镜像？ | **平台**控制。用户不能自带镜像 | 降低风险 |
| 谁控制网络？ | **平台**控制。每实例独立网段，桥端口只发布到宿主回环 | 降低风险 |
| 谁控制凭据？ | **平台**控制。零跨实例凭据共享 | 降低风险 |
| 用户能执行什么？ | **任意 shell 命令**。这是 dsh 的本职功能 | 提升风险 |
| 用户能安装什么？ | **任意 npm / pip / apt 包**。rootfs 可写 | 提升风险 |
| 用户能出网吗？ | **能**。无 egress 过滤 | 提升风险 |
| 有没有应用层纵深？ | **有**。dsh 自身有进程沙箱（bubblewrap / Landlock）；入口有三道门 | 降低风险 |

综合：用户可以执行任意代码（这把它推离「可信」档），但平台控制镜像、网络、凭据，
且有应用层纵深（这把它从「不可信」拉回来）。**落在第 ② 档：半可信。**

### 3.3 为什么不是第 ③ 档

第 ③ 档需要 gVisor 或 microVM。两个都量过，都跑不了：

| 运行时 | 结果 | 原因 |
|---|---|---|
| **gVisor（runsc）** | ❌ 不能跑 | dsh 的沙箱链（bubblewrap / Landlock）在用户态内核下全灭——`EPERM` / `ENOSYS`。按 dsh 的 fail-closed 语义，拒绝执行任何命令 |
| **microVM（Kata / Firecracker）** | ❌ 跑不了 | 需要 `/dev/kvm`（硬件虚拟化），多数 VPS 不开嵌套虚拟化 |

**这不是「Docker 够安全所以不上 microVM」**，
而是「当前的硬件条件和 dsh 的兼容性决定了只能用 Docker，
所以需要在 Docker 上把纵深防御做到可接受的水平」。

这条决定写在 [D2](DECISIONS.md)，附带四个重审触发条件：

1. 客户合规要求内核级隔离
2. 允许安装不可信的第三方插件
3. 规模上去了需要更高密度
4. 出现了影响当前加固措施的新攻击向量

## 四、隔离需求矩阵

把威胁模型（§2.2）和信任等级（§3.2）结合，得出每条通道的隔离需求：

### 4.1 网络

| 需求 | 优先级 | 手段 | 状态 |
|---|---|---|---|
| 实例之间不能直连 | **必须** | 每实例一个 Docker 网络（`dsh-net-<slug>`） | ✅ 已实现 |
| 实例端口不对局域网暴露 | **必须** | 桥端口只发布到宿主回环 `127.0.0.1` | ✅ 已实现 |
| 实例不能碰宿主上的非回环服务 | 推荐 | 宿主侧 INPUT 规则（`install.sh --harden-host`） | ⚙️ 可选 |
| 实例出网受限 | 推荐 | 宿主侧 iptables / nftables | ❌ 未做 |

### 4.2 存储

| 需求 | 优先级 | 手段 | 状态 |
|---|---|---|---|
| 每实例独立数据目录 | **必须** | 池子里的 `<pool>/<key>`，按 `storage_key` 定位 | ✅ 已实现 |
| 磁盘空间硬限 | **必须**（Linux） | XFS project quota（字节 + inode 双限） | ✅ 已实现 |
| 设不上配额 = 拒绝启动 | **必须** | 启动自检，显式失败 | ✅ 已实现 |
| 删容器不删数据 | **必须** | 容器与卷解耦 | ✅ 已实现 |

### 4.3 凭据

| 需求 | 优先级 | 手段 | 状态 |
|---|---|---|---|
| 实例内无 DB 凭据 | **必须** | 不注入 | ✅ 已实现 |
| 实例内无平台密钥 | **必须** | 不注入 | ✅ 已实现 |
| 实例内无 Docker socket | **必须** | 不挂载 | ✅ 已实现 |
| 实例内无全局共享 HMAC | **必须** | 每实例独立派生的门 token | ✅ 已实现 |

### 4.4 访问控制（三道门）

| 门 | 挡什么 | 手段 | 状态 |
|---|---|---|---|
| ① 网络隔离 | 实例之间直连 | 每实例独立网络 + 回环发布 | ✅ 已实现 |
| ② 入口认证 | 未登录 / 非 owner 访问 | Traefik forward-auth → 平台认证 + 授权 | ✅ 已实现 |
| ③ 桥门 | 绕过入口直连容器端口 | Caddy 校验 HMAC 签名 header | ✅ 已实现 |

**三道门的关系**：Linux 上 ① 是主力、③ 是纵深；Docker Desktop 上 ① 的回环半条被
`host.docker.internal` 绕开，此时 ③ 是最后一道。②  在两个平台上都独立工作。

### 4.5 资源限制

| 需求 | 优先级 | 手段 | 状态 |
|---|---|---|---|
| 内存上限 | **必须** | `HostConfig.Memory` | ✅ 已实现 |
| CPU 上限 | **必须** | `HostConfig.NanoCpus` | ✅ 已实现 |
| 进程数上限 | **必须** | `HostConfig.PidsLimit`（默认 512） | ✅ 已实现 |
| 磁盘空间上限 | **必须**（Linux） | XFS project quota | ✅ 已实现 |
| 磁盘 I/O 限制 | 低 | blkio / io.max | ❌ 未做 |
| 网络带宽限制 | 低 | TC 规则 | ❌ 未做 |

### 4.6 加固

| 需求 | 优先级 | 手段 | 状态 |
|---|---|---|---|
| 禁 `--privileged` | **必须** | 不使用 | ✅ 已实现 |
| MaskedPaths | **必须** | Docker 默认 + DMI 遮罩 | ✅ 已实现 |
| CapDrop | 推荐 | `--cap-drop=ALL` + 按需 `--cap-add` | ⚠️ 未做 |
| `no-new-privileges` | 推荐 | `--security-opt=no-new-privileges:true` | ⚠️ 未做 |
| seccomp 收紧 | 推荐 | 在默认 profile 基础上进一步收紧 | ⚠️ 未做 |
| ReadonlyPaths 显式设置 | 低 | 显式写死代替依赖 Docker 默认 | ⚠️ 未做 |
| userns-remap | 低 | 容器 root → 宿主非特权 UID | ⚠️ 未做 |

### 4.7 Web 层

| 需求 | 优先级 | 手段 | 状态 |
|---|---|---|---|
| 实例子域不能代行控制面操作 | **必须** | Origin 检查 + trusted origins 白名单 | ✅ 已实现 |
| 平台 cookie 不传给实例后端 | **必须** | 入口 cookie 过滤 | ✅ 已实现 |
| 实例不能种覆盖父域的 cookie | 推荐 | 短时 token 替代父域 cookie（OPEN-QUESTIONS #13） | ❌ 未做 |

## 五、接受的代价与残余风险

选择 Docker + 纵深防御、而不是 microVM，意味着主动接受了以下代价：

### 5.1 结构性的（Docker 改不了）

| 代价 | 影响 | 缓解 |
|---|---|---|
| **共享内核 → 逃逸即宿主失陷** | 所有实例 + 宿主一起沦陷 | seccomp（默认 profile）、MaskedPaths、未来 CapDrop / no-new-privileges |
| **`/proc` 信息泄漏** | 实例可指纹宿主、推断邻居负载 | lxcfs（可选，遮三个文件）；`sysinfo(2)` 绕得开 |
| **无原生 egress 过滤** | 实例可以访问任意外部地址 | 宿主侧 iptables（可选） |

### 5.2 当前未做到的（Docker 能做，还没做）

| 项 | 风险 | 计划 |
|---|---|---|
| CapDrop | 容器保留 ~14 条默认 capability | 需要逐条验证 dsh 的兼容性后收紧 |
| `no-new-privileges` | 容器内 setuid 二进制可提权 | 同上 |
| seccomp 收紧 | 默认 profile 允许 ~300 个 syscall | 需要 profile 定制 |
| ReadonlyPaths 显式化 | 依赖 Docker 默认值，版本间可能漂移 | 照抄写死 + 测试守着 |
| 容器内降权 | 工作负载跑 root | 需要解决卷权限问题 |
| 出网过滤 | 实例可任意出网 | M2 |
| 同注册域 cookie 投毒 | 实例响应可种覆盖父域的 cookie | OPEN-QUESTIONS #13 |

### 5.3 平台级的（不在运行时层面）

| 代价 | 说明 |
|---|---|
| **开发机上的隔离是降级的** | Docker Desktop 的 `host.docker.internal` 绕开回环边界；linuxkit 内核没有 XFS quota / Landlock |
| **宿主运营者不受应用层限制** | 有宿主 / Docker 权限 = 能碰一切。平台不做静态加密 |
| **日志可能含敏感内容** | 容器输出可能含用户密钥，管理员能看日志 |
| **非运行时跨实例通道** | 备份脚本、控制面查询、日志聚合——每一处都必须带实例维度 |

## 六、升级路径

当前的 Docker 隔离方案不是终态。设计上预留了运行时可插拔的接缝：

```
业务层（provisioner / boot / reconciler）
           │
           ▼
    runtime/driver.ts  ← 唯一接触具体运行时的接口
           │
           ▼
    packages/instance-spec  ← 纯描述，零 I/O
```

换运行时只需要换 driver 层的实现。业务层不认识任何具体运行时。

**可能的升级路径**（D2）：

```
当前                          下一步
────────────────────          ──────────────────────
Docker (runc)                 K8s + containerd
  └─ 每实例一个网络              └─ runtimeClass: kata
  └─ XFS project quota            └─ 每 Pod 一个 microVM
  └─ 桥端口回环发布                └─ 硬件级内核隔离
```

**不要**走裸 Firecracker——直接管 microVM 的运维成本
（镜像分发、网络接入、存储挂载）远高于经 K8s containerd 间接使用。

## 七、总结

| 问题 | 答案 |
|---|---|
| 这个平台在隔离什么？ | 跑着 AI agent 的多个容器——每个容器里有任意代码执行能力 |
| 要隔离到什么程度？ | 一个实例被攻陷不能影响另一个实例。宿主的安全依赖加固降低概率，但不消除 |
| 信任等级是什么？ | **半可信**（第 ② 档）：平台控制镜像 / 网络 / 凭据，用户可执行任意命令 |
| 为什么用 Docker？ | gVisor 与 dsh 不兼容，microVM 需要宿主没有的硬件支持。这是约束下的最佳选择 |
| 天花板在哪？ | 共享内核。逃逸即宿主失陷，这条加固收不掉 |
| 什么时候需要换？ | 合规要求内核隔离 / 允许不可信插件 / 新攻击向量 / 规模需要更高密度 |
